# Inference broker contract

The broker is the only external-model interface. It has no production in-memory source of truth: a production `InferenceBackend` must atomically persist `inference_requests`, manifests, attempt leases/fences, cost reservations, attempts, and append-only events before it reports outward success. `SQLiteTestInferenceBackend` exists only for isolated tests; the parent integration supplies the Postgres implementation.

## Backend contract

`create_or_get()` enforces the semantic request idempotency key and stores the context manifest. An idempotency key is bound to one semantic task and one manifest hash: a mismatched reuse raises `IdempotencyConflict`, not cache reuse. `claim_attempt()` allocates a monotonic attempt number and fencing token under a lease. `reserve_cost()` must atomically enforce the semantic total budget over both accrued failed attempts and outstanding reservations, including conservative reservations for billable failed/time-out calls. `finish_attempt()` must reject stale fences and late competing accepted results; a losing late response is persisted as a cost-bearing, non-authoritative `HIBERNATED` attempt without its artifact, so no provider spend disappears or becomes gate evidence. `hibernate()` leaves a durable requeueable state and can never overwrite an accepted result. Route recovery is explicit through `revive_route()`; it is reserved for an independent health probe or approved operational recovery, never inferred from the failed task. A downstream deterministic gate may call `mark_decision_useful()` to record the fourth success layer; semantic acceptance alone never asserts usefulness.

`InferenceBackend` is a runtime-checkable structural protocol, so the production Postgres adapter can satisfy it without inheriting a test implementation. Its operations are transaction boundaries: the production adapter must enforce fencing in SQL. Attempts persist pricing-plan identity, fixed/token components, billed-token count, the provider-reported model label, and any later provider-reported cost. Provider labels remain assertions, not proof of identity.

Provider credentials are resolved only at transport time, after the configured hostname resolves exclusively to global IP addresses. The broker never logs prompt content, API keys, or authorization headers. Route URLs are HTTPS and configured-host allowlisted; callers cannot choose arbitrary endpoints. DNS validation is an application-layer defense and production deployment still needs network egress allowlisting to close DNS-rebinding races. A route records separate provider, endpoint, and key-pool IDs, and its license/terms clearance. `config/providers.example.json` is intentionally non-operational until an owner configures a real allowed endpoint, benchmarked model identity, pricing, and secret resolver.

## Context and egress

`ContextCompiler` requires a task contract, matching request/contract schemas, evidence classes, explicit retrieval status, egress classification, and an evidence manifest. It distinguishes `NOT_RETRIEVED` from an affirmatively justified `NOT_RELEVANT`; a critical missing, inaccessible, contract-declared, or unexpanded required evidence class fails closed. Critical decisions additionally require an explicit `adverse_facts` class, which may only be absent through a declared no-adverse-facts evidence item. SECRET content never enters an ordinary prompt, SEALED material requires an appropriately cleared route, and license restrictions apply equally to memories and tool expansions. Summary references preserve canonical source IDs. Tool-addressable material is recorded and expansions are appended to the manifest. `ContextCompiler.apply_tool_expansion()` returns a new immutable context that attaches the approved source to the prompt package and updates its manifest hash; a manifest-only mutation is not sufficient evidence of what the provider received. Fallback routes must have sufficient egress clearance for both inline and tool-addressable evidence and cannot relax a no-training/known-retention decision for confidential material.

Fresh reviewers receive only their controlled package. A critical-review scheduler must persist an independence profile (model family/version, correlation domain, mandate, prompt version, ordering, prior-verdict visibility, tools/retrieval policy) and reject nominal reviewer padding without meaningful diversity. `ReviewIndependencePolicy.assess_batch()` emits explicit residual same-model and shared-upstream correlation flags; these residual limitations remain evidence rather than being hidden by quorum count. Same-family reviewers require distinct mandates and evidence-ordering profiles. The broker exposes route correlation domains specifically so shared reseller/key routes are not treated as independent fallback.

## Routing and accounting

Routes are selected lexicographically for capability/quality/reliability/deadline eligibility then expected accepted-result economics: provider-specific pricing includes fixed, input/output/reasoning/cache, minimum and billable-failure semantics plus observed rework. Requests may require a `routing_benchmark_id`; only routes with nonzero controlled task-class observations from that exact benchmark are eligible, preventing incomparable selective routing histories from being treated as calibrated quality. Each individual attempt reserves direct estimated provider cost; missing usage and transport timeout charge a conservative configured reserve. Route/model labels are claims, not proof; `identity_assurance` and benchmarked task-class quality control eligibility. Common benchmark/challenger traffic must be budgeted separately to avoid routing selection bias.

When any estimated usage dimension is unknown, the broker fills it from the route's `unknown_usage_reserve` before admission, reservation, and max-call-cost comparison. This prevents a partial estimate from bypassing a request budget. The example registry is deliberately non-operational and includes reserve fields owners must calibrate from provider billing limits.

Accepted output requires transport, strict JSON schema, and optional task-specific semantic validation. Before rejection, the broker deterministically recovers one uniquely parseable JSON object from fenced or surrounding prose; ambiguous multiple artifacts remain rejected rather than choosing a convenient answer. Empty, refusal-like, malformed, and truncated output is not a semantic success. Failures use independent correlation-domain fallback and durable hibernation rather than blind retries. Reconciliation compares provider billing with persisted estimates, emits a billing discrepancy event before exact-cost claims, and replaces accrued estimated spend with the provider-reported amount.
